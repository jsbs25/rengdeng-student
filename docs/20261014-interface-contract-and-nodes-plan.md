## 2. `/api/nodes` 60 并发复盘

### 已上线的保护机制

`/api/nodes` 已使用 stale-while-revalidate 语义：请求只读最近成功快照，过期时只启动一个 daemon refresh worker；抓取和测速不会占用请求线程等待时间。刷新失败会保留旧缓存；冷缓存也快速返回可识别的空节点状态。

本轮日志再次确认：300 个并发请求在过期缓存状态下只触发 **1 个**后台刷新。刷新期间 4 个外部源返回 404，但 worker 没有失败：测速完成后成功写入 **559 bytes** 快照，得到 **3 个节点**。

### 真实公网测试数据

| 压测情境 | 请求 / 成功 | 缓存状态 | P50 | P95 | P99 | 最大值 |
|---|---:|---|---:|---:|---:|---:|
| 60 并发、过期缓存 | 300 / 300 | `refreshing=true`, `stale=true` | 139.59ms | 6.56s | — | 6.92s |
| 60 并发、热缓存 | 300 / 300 | `refreshing=false`, `stale=false` | 231.80ms | 1.50s | — | 2.95s |
| 20 并发、第 1 波 | 100 / 100 | 热缓存 | 128.66ms | 2.91s | 3.92s | 3.92s |
| 20 并发、第 2 波 | 100 / 100 | 热缓存 | 126.98ms | 213.91ms | 1.13s | 1.14s |
| 20 并发、第 3 波 | 100 / 100 | 热缓存 | 133.56ms | 355.21ms | 365.50ms | 376.44ms |

### 判断

- **正确性与可用性正常：** 600 / 600 请求成功，缓存命中与单飞刷新均正确，没有 5xx、超时或服务重启。
- **待处理问题是尾延迟，不是第三方抓取阻塞：** 刷新已在后台隔离。60 个瞬时新连接仍会放大公网反向代理/TLS、Python `ThreadingHTTPServer` 接收队列、每次响应 JSON 序列化以及线程调度的尾部等待。
- **外源质量是独立事项：** 当前 5 个订阅地址中有 4 个返回 404；旧快照和可用来源保证了服务可用，但应进行受控的来源健康治理，不应在请求路径上重试或扩大抓取。

## 3. 下一阶段具体优化方案

### 阶段 A：把热缓存读取改成预序列化快路径

**目标：** 让 `/api/nodes` 的正常请求只进行“读取不可变 bytes + 写回响应”，避免每个请求重复 YAML 解析、节点提取或 `json.dumps()`。

1. 在刷新 worker 成功时同时生成：
   - YAML 文本快照；
   - JSON 对象快照；
   - 已 UTF-8 编码的 JSON bytes；
   - `Content-Length` 与缓存状态元数据。
2. 用短锁完成一次引用交换；读请求只读取最新不可变快照引用，不持锁进行序列化。
3. 为接口增加 `X-NOUR-Node-Generation`、`X-NOUR-Cache-Age`、`X-NOUR-Refresh-State` 诊断头；不包含来源 URL、用户或密钥。
4. 保留当前 JSON 合同：`ok/count/nodes/sub/refreshing/stale/age_seconds/last_success` 不变。

**预期收益：** 降低应用层每请求 CPU 与锁竞争；是风险最低、最应先做的一步。

### 阶段 B：治理连接突发，而不是放大线程数

**目标：** 把瞬时连接尖峰与应用层缓存读取隔离。

1. 在反向代理中对 `/api/nodes` 启用 **1–3 秒微缓存**与请求合并（cache lock / request coalescing）；只缓存公开节点快照，短 TTL 不改变用户可见语义。
2. 保持上游 HTTP keep-alive，避免 60 个新请求都重复建立到 Python 的短连接。
3. 将 HTTP 服务的接收队列容量显式设置为不少于 128，并记录排队等待时间；不要用无界线程扩张掩盖问题。
4. 对每次压测分别记录：边缘连接耗时、上游等待、应用序列化、总响应时间；只有瓶颈明确后才调整代理参数。

**建议验收：** 60 并发热缓存下 100% 成功；在相同公网测试点将 P95 稳定控制在 **≤ 750ms**、P99 **≤ 1.5s**。若外部网络抖动扩大总时延，应将边缘时间与应用时间拆分报告。

### 阶段 C：刷新与来源健康治理

**目标：** 即使外部源持续失效，刷新仍然轻量、可退避且可观察。

1. 将“最后成功 YAML / JSON / 时间戳 / generation”持久化为单个原子快照文件；服务重启后立即可服务旧快照。
2. 为每个既有来源保存最少元数据：最近 HTTP 状态、持续失败次数、下一次允许尝试时间；不记录用户信息。
3. 对 404、429、超时采用指数退避；刷新一次失败不能清空已有成功节点。
4. 对当前连续 404 的 4 个来源单独人工核验后替换或移除，避免在用户请求触发的刷新周期中浪费连接预算。
5. 保持每来源 1–2 秒连接/读取超时、有限测速候选与单飞锁；不增加爬取规模。

### 阶段 D：可观测性与发布门槛

新增低基数统计与结构化日志：

| 指标 | 用途 |
|---|---|
| `nodes_cache_hit_total` / `nodes_cache_stale_total` | 缓存命中和陈旧快照比例 |
| `nodes_refresh_started_total` / `nodes_refresh_success_total` / `nodes_refresh_failure_total` | 单飞与刷新可靠性 |
| `nodes_response_ms`（P50/P95/P99） | 用户实际延迟 |
| `nodes_queue_wait_ms` | 判断是否为连接/线程排队 |
| `nodes_snapshot_generation` | 确认并发请求使用同一快照 |
| `nodes_source_status_total` | 外部来源失效趋势 |

每次变更保持现有发布纪律：独立备份 → staging 语法检查 → 最小原子替换 → systemd 检查 → 公网冷/热/过期三态压测 → 健康监控确认。

## 4. 今日一句与完整句子库验证

| 项目 | 结果 |
|---|---|
| `/api/sentences/daily` | HTTP 200；生产响应约 216 bytes；返回真实句子 `item` |
| 首页首屏 | 只请求 `/api/sentences/daily`；不请求完整 `/api/sentences` |
| 完整句子库 | 用户主动加载 `builtin_sentences.js`；本地专项验证加载 **33,049** 条真实句子 |
| 移动首页（390×844） | 13 / 13 通过 |
| 桌面首页（1280×900） | 13 / 13 通过 |
| 主题与 RTL/LTR | 12 / 12 通过 |
| 古兰经入口与阅读器 | 8 / 8 通过 |
| OpenITI 流式阅读器 | 16 / 16 通过 |
| 移动端任务条专项 | 6 / 6 通过 |

历史“全资产连续加载”浏览器脚本在本机把六组大资源连续装入同一个非持久 WebKit 页面时超过 300 秒；本轮改用更贴近用户路径的专项验证，确认首屏不加载完整句子库，主动加载在 60 秒内完成。该压力脚本可在后续专门分拆为按资源独立计时的性能回归，避免把累积 WebKit 内存行为误判为首屏回归。
