# 燃灯同学 / NOUR 2.0 阶段 7：性能治理与阿拉伯语词典增强计划

**计划日期：** 2026-10-06  
**当前状态：** 规划完成，尚未修改生产代码或发布  
**实施顺序：** 性能基线 → 低风险性能修复 → 词典索引 → 词典工作区增强 → 公网验收

## 1. 本阶段决策

本阶段不在“全站性能优化”和“词典新特性”之间二选一，而采用两段式推进：

1. **阶段 7A：性能治理先行。** 先减少首屏不必要的脚本下载、重复缓存失效和查词冷启动成本。性能修复完成后，才把新增词典功能接入，避免在慢页面上继续叠加代码。
2. **阶段 7B：词典能力增强。** 以现有本地词典、句子库、词根/词形课程和现有生词本为真实来源；不杜撰词根、词性、词源或学派信息。模型分析只在用户明确点击后触发，并标记为“模型分析 / 需核验”。

本阶段**不迁移 FastAPI、不替换 `server.py`、不删除旧页面、不删除任何数据、不改变现有 `/api/*` 路径和 localStorage 键**。

## 2. 当前可复现实测基线

| 项目 | 当前值 | 影响 |
|---|---:|---|
| 生成首页 `arabic_learning.html` | 约 1.90 MB | HTML 本身包含大量页面结构和内联脚本 |
| `build_home.py` | 约 650 KB | 构建维护成本高，不能直接整文件重写 |
| 内置句子脚本 | 约 4.82 MB | 不应在首页首屏无条件下载 |
| 内置书籍脚本 | 约 2.34 MB | 书库页面才需要优先加载 |
| 内置古兰经脚本 | 约 2.21 MB | 古兰经入口打开时再加载更合理 |
| `data.json` | 约 4.97 MB，29,709 条 | 当前查词会在句子列表中逐条扫描 |
| `vocab_meanings.json` | 295 条释义 | 当前固定释义规模有限，不能假装是完整词典 |
| 页级 AI Flash 长页样本 | 6,316 ms / 4,366 tokens | 保持缓存、页文本上限和证据字段，不用“降质”换表面速度 |
| 公网 API 压测 P50 / P95 | 158 ms / 1,004 ms | 以只读接口为主，不把 AI、TTS、ASR 混入普通 API SLA |

当前查词链路已经具备：本地优先、无模型查询、例句、相近词形、公开 Wiktionary 补充、设备朗读和“交给 NOUR AI”按钮。主要技术问题是：

- `_local_dict_lookup()` 第一次加载后会逐条扫描句子寻找例句；
- 缓存失效时间主要跟随 `vocab_meanings.json`，句子库变化不能精确触发重载；
- 内置大脚本虽然使用 `defer`，但仍会在页面启动阶段发起下载；
- HTML/JSON/JS/CSS 当前普遍使用 `no-store`，每次刷新可能重新传输大静态资源；
- 主题和产品壳经过多层内联覆盖，性能修改必须先做浏览器水合/加载顺序回归。

## 3. 阶段 7A：性能治理实施范围

### 7A-0：建立网络与内存基线

只读测量，不改业务：

- 手机 390×844、桌面 1280×900 各测冷启动和刷新启动；
- 记录 HTML、CSS、JS、JSON 的请求数量、传输字节、压缩后字节、首个可交互时间；
- 记录首页、书库、阅读器、AI、词典首次打开的网络瀑布；
- 记录本地服务与公网服务的 RSS、请求延迟 P50/P95、错误率；
- 分开记录“首屏下载”和“用户点击后按需下载”，避免把延迟归因混淆；
- 不调用真实付费 AI、TTS、ASR、支付、登录或管理接口进行压力测试。

输出：`docs/20261006-phase7-performance-baseline.json` 与配套 Markdown 报告。基线报告只保留聚合指标，不写入密钥、用户数据或完整模型返回。

### 7A-1：静态资源缓存治理

在不改变内容的前提下逐步处理：

- 为生成产物和内置大脚本加入构建版本/内容指纹，避免“永远不缓存”和“旧脚本被缓存”二选一；
- 对带版本标识的静态资源使用公开缓存，对 HTML 使用短缓存或协商缓存；
- 增加 `ETag` / `Last-Modified` 条件请求验证；
- 保留 `Vary: Accept-Encoding`，继续使用 gzip；
- 不缓存用户、支付、解锁、AI key、会员状态、用户历史和任何写接口响应；
- 不在本阶段改变 OpenITI/Shamela 正文缓存和按需读取边界。

实施时优先修改 `_serve()` 的响应头和构建器生成的资源 URL，并先验证 Safari/Chrome 的版本切换不会读取旧 JS。

### 7A-2：按需加载内置数据

把当前“页面启动即请求”的大数据脚本改为兼容式加载器：

- 首页只保留产品壳、必要的轻量配置和统计；
- 打开“全部句子”时才加载 `builtin_sentences.js`；
- 打开书架/旧书库入口时才加载 `builtin_books.js`；
- 打开古兰经时才加载 `builtin_quran.js`；
- 打开六大部圣训、词汇表、历史库和课程时分别按需加载对应资源；
- 每个资源只加载一次，使用 Promise 复用并在失败时显示明确的重试入口；
- 本地离线/旧浏览器路径保留现有空数组兜底和真实 API 兜底；
- 任何函数调用前必须等待对应资源 ready，不靠“延迟 600ms”猜测脚本是否已到达。

这一项必须逐页面迁移，先迁句子和书籍，再迁古兰经与圣训，不能一次性删除原有全局变量。

### 7A-3：服务端查词索引化

新增构建脚本，例如 `tools/build_dictionary_index.py`，只使用项目已有真实文件：

- `data/vocab_meanings.json`：固定释义；
- `data/data.json`：真实例句；
- 现有词法/语法教学数据：仅作为课程入口，不把课程示例伪装成完整词典释义。

索引建议：

- 规范化词形 → 固定释义；
- 规范化词形 → 最多 6 条例句 ID；
- 词形前缀/包含关系的有界候选；
- 生成文件带源文件 mtime/hash 和版本号；
- 索引生成失败时继续使用旧逐条扫描逻辑，不能导致查词接口整体不可用。

服务端加载时按索引文件 mtime/hash 做一次性缓存；热路径不再每次遍历 29,709 条句子。`/api/dict/lookup?w=` 保持兼容，现有字段继续返回：`ok`、`found`、`word`、`normalized`、`meaning`、`examples`、`matches`、`source`、`offline`。

## 4. 阶段 7B：阿拉伯语词典增强

### 4.1 新增能力边界

词典增强分为三层，清楚区分来源：

1. **本地确定层**：固定释义、现有例句、规范化词形、相近词形、朗读、生词本。
2. **课程关联层**：链接到已有“词根与派生”“语法课”“词法课”等真实课程条目；如果课程中没有该词根，只显示“暂无本地课程条目”。
3. **显式 AI 层**：用户点击“交给 NOUR AI 分析”后，基于当前词、当前阅读页和选中的句子请求模型；输出必须拆分“确定信息 / 模型推断 / 需要核验”，不把模型结果写回固定词典释义。

本阶段不把 Wiktionary、AI 或外部搜索结果冒充本地权威词典；外部来源继续以“公开补充”单独显示。

### 4.2 词典工作区 UI

保留现有 `openDict()`、`dictSearch()`、`rdWord()`、`wbAdd2()` 和阅读器词卡入口，追加：

- 阿拉伯词头使用 `dir="rtl" lang="ar"`；中文释义独立使用 `dir="ltr"`；混合字符串使用隔离包装，避免“阿语和中文倒置”；
- 结果分成“释义、例句、相近词形、学习关联、NOUR AI”几个区域；
- 显示来源标签：本地词库、句子库、公开词典、模型分析；
- 增加最近查词记录，使用独立版本化 localStorage 键，不覆盖既有生词本和历史记录；
- 查词结果在当前会话短缓存，重复打开不重复请求；
- 手机词卡保留底部安全区，桌面不遮挡阅读器正文；
- 夜间模式下保证词头、中文释义、例句和来源有足够对比度；
- “收藏”仍走现有生词本，不创建第二套词汇数据。

### 4.3 可选 API 扩展

不改变旧接口，先考虑增加只读、有界参数：

- `/api/dict/suggest?q=&limit=20`：只返回候选词头和简短中文释义；
- `/api/dict/lookup?w=&examples=6`：允许前端明确请求例句数量，服务端强制上限；
- `/api/dict/lesson?w=`：只返回已有语法/词法课程中明确命中的条目；
- `/api/dict/ai`：如确有必要，再复用现有聊天/额度/上下文管线，不复制另一套 AI 计费逻辑。

所有参数必须限长、限结果数、只读；不得因为补全输入就请求外部站点或模型。

## 5. 测试门槛

### 性能测试

- `tools/performance_baseline.py`：记录静态资源、接口延迟和响应大小；
- `tools/dictionary_lookup_benchmark.py`：冷启动/热缓存各 20–50 个真实词形，记录 P50/P95；
- `tools/static_cache_contract.py`：检查版本资源的缓存头、条件请求和 gzip；
- 内存检查：索引加载后 RSS 增量有记录，不允许无限复制 `data.json`；
- 首屏专项：证明首页不再自动下载未使用的句子/书籍/古兰经大脚本。

### 词典浏览器回归

新增或扩展 `tools/dictionary_word_card_ui_test.js`，手机和桌面各执行：

- 本地命中词：`كِتَاب` / `كتاب`；
- 无音符规范化命中；
- 相近词形和例句展示；
- 外部公开补充不覆盖本地结果；
- “交给 NOUR AI”能传递词和阅读页语境；
- 收藏进入既有生词本；
- 夜间模式、中阿方向、键盘 Enter 查词、朗读按钮；
- 网络失败时显示可重试状态，不显示空白或假释义。

### 旧功能回归

每次发布前至少执行：

- `python3 -m py_compile server.py build_home.py openiti_stream.py`；

- 经典索引与四学派阅读室；
- 首页/导航/学习工作台；
- Apple Books 风格阅读器、书签、页级 AI；
- 古兰经入口、经注、诵读；
- 主题日夜与中阿混排；
- 8,794 目录、8,589 Shamela 索引、239 页《مختصر القدوري》接口；
- 手机 390×844 与桌面 1280×900 浏览器回归。

## 6. 暂定验收目标

这些是工程目标，不是未经实测的承诺；以阶段 7A-0 实测基线为准调整：

- 首页首屏不请求用户未打开的 4–5 MB 以上内置大脚本；
- 首页初始静态资源传输量较当前基线明显下降，并在二次刷新中命中版本缓存；
- 本地查词热路径目标：P95 ≤ 150 ms；冷启动目标：P95 ≤ 500 ms；
- `/api/dict/lookup` 在索引缺失时仍可用，只允许性能降级，不允许功能消失；
- 手机词卡和 AI 输入区不被底部导航遮挡；
- 目录总数仍为 8,794，Shamela 可读索引仍为 8,589；
- 不出现 522、413、OOM；OpenITI 超大书仍走流式/范围读取；
- `nur.service` 与 `nur-health-monitor.service` 保持 `active`。

## 7. 发布与回滚

每一个子阶段单独发布：

1. 本地建立代码和构建产物校验；
2. 远端创建独立备份，例如 `/opt/nur/backups/20261006-phase7-performance-dictionary-v1`；
3. 只上传必要的 `server.py`、`build_home.py`、构建 HTML、相关 `data/*.js/css/json`、测试脚本和报告；
4. 明确排除 `data/ai_key.txt`、`ai_keys.json`、users、payments、unlocks、缓存和监控日志；
5. staging 目录执行 Python 语法、资源存在性和 API 合同检查；
6. 最小原子替换，重启 `nur.service`；
7. 验证服务和健康监控 active，再做公网 API/浏览器验收；
8. 任何核心回归失败立即停止，不叠加下一子阶段；
9. 保留一键恢复上一回滚目录的命令和报告。

## 8. 不在本阶段做的事情

- 不把 FastAPI/Uvicorn 直接引入生产；
- 不重写 650 KB 的 `build_home.py`；
- 不批量抓取或复制受版权保护的外部全文；
- 不把 AI 生成内容写入权威词典或作为法学证据；
- 不自动升级到更昂贵模型；
- 不删除旧导航、书库、古兰经、六大部、语音、学习记录或任何既有数据；
- 不用静态截图伪装加载、查词、阅读或 AI 能力。
